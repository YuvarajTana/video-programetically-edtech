# Authoring guide

Editorial rules for writing video specs. Validation enforces the measurable
ones (`npm run validate`); the rest are judgment calls this page makes
explicit. Adapted from the AIDD handoff spec, where each rule has a measured
basis.

## The two naming rules

These are different jobs, and both matter:

1. **The video `title` is the subject name** — what someone would type into a
   search box. Good: "KV Cache", "Binary Search", "Hallucination". Bad:
   "Token 500 Should Be Slow". It drives the cover, metadata, and packaging.
2. **The first frame is a hook, not a label.** The opening scene makes a
   claim, asks a question, or shows something wrong — the channel chrome
   already identifies the video from frame one. Validation warns when the
   opening title just repeats the video title.

| Bad frame one | Good frame one |
| --- | --- |
| `Tokens` | `You are not billed for words.` |
| `Inference` | `It cannot see the end of its own sentence.` |

## Narration is captions

Most feed views are muted: every narration line is also the on-screen
caption, so the lines must carry the video alone.

- **Max ~10 words a line.** If it needs a comma to survive, split it.
- **One idea per line. Active voice.** "The model cuts your text", not "your
  text is cut".
- **No idioms, no phrasal verbs.** "Budget for that", not "factor that in".
- **Say the number.** "Three times the tokens" beats "significantly more".
- **Read it aloud.** If you stumble, a reader with English as a second or
  third language stumbles harder.

### Pace

Target **2.2–2.8 words per second** (the tech channel band is 130–165 WPM).
`voiceover.md` (regenerated by `npm run captions`) shows per-scene pace with
`⚠ fast` and `· slow` flags — fix every `⚠` before recording or synthesis.
Validation warns above the ceiling everywhere, and below the floor only on
text-led scenes (title/callout/bigStat), where a slow line over a static
frame reads as dead air.

## Every scene shows a mechanism

Something should move, fill, travel, flip, get eliminated, or get blocked.
Text-led scenes (`title`, `callout`, `bigStat`) are for the hook, the
verdict, and the recap — validation warns when one holds a static frame for
more than six seconds mid-video. Aim for a visual change every 3–5 seconds.

**Front-load the payoff.** If the useful part lands at 40 seconds, everyone
who left at 20 seconds got nothing.

## Accents

Accent roles are semantic and fixed: `success` = correct, `attention` =
focus/problem-adjacent, `info` = explanation, and they must never be swapped.
When you set accents explicitly, rotate them — validation warns when two
adjacent scenes declare the same accent.

## The house cast

Reuse the same names, places, and schema across videos instead of inventing a
parallel cast each time:

- **People:** Ravi, Priya, Meera
- **Places:** Chennai, Pune, Bengaluru
- **Money:** rupee amounts (₹), GST where tax appears
- **Data:** the e-commerce schema — `users`, `orders`, `order_items`

## Accuracy

- Never present an invented number as measured. Round, illustrative figures
  are fine — label them illustrative in the spec's comments and post copy.
- If a topic has a commonly repeated oversimplification, say the correct
  thing. Being right matters more than being neat.
- Unsure of a detail? Leave it out rather than guess. Tech videos citing
  statistics need `editorial.sources` (validation reminds you).

## Workflow

```bash
npm run new -- --channel tech --template concept-explainer my-slug "My Topic"
npm run validate -- tech/my-slug     # fix errors, then take warnings seriously
npm run captions -- tech/my-slug     # check the pace column in voiceover.md
npm run studio                       # scrub for collisions and dead air
npm run produce -- tech/my-slug
```

To have a model draft the spec, use
[`docs/llm-authoring-prompt.md`](llm-authoring-prompt.md).
